# v0.8: compatibility and upgrades

Status: released as v0.8.0 on 2026-10-01. This does not claim that all
v1 qualification gates have passed. Schema remains version 4.

## Scope

- Reject unknown or corrupt migration history before applying SQL. Surface
  classifiable errors to SDK callers and clear startup/doctor diagnostics.
- Protect existing ordering/Inbox down-migration guards from concurrent writes.
- Freeze published migration bytes and test upgrade preservation from every
  released schema prefix, including opaque payloads and legacy Inbox markers.
- Normalize named reserved headers to prevent ambiguous event identity while
  preserving application headers and durable replay provenance.
- Document public package contracts and compile representative external API
  usage in CI. Preserve current public signatures and wire identities.
- Document binary rollback separately from schema rollback, retention and
  backup/restore boundaries. Keep infrastructure support claims tied to evidence.

## Acceptance

- Invalid history is refused by up, down and inspection without data changes.
- Fresh install, repeated up and supported prefix upgrades preserve data.
- Unfinished managed Inbox and ordered cursors prevent destructive downgrade.
- Released migration files remain unchanged. Public client fixtures compile.
- Unit, integration and vet results are recorded against the candidate SHA;
  race, longer soak and release checks remain explicit gates until completed.

## Crash and concurrency review

Migration SQL and history updates commit in one PostgreSQL transaction. Death
before commit rolls back; death after commit leaves a complete durable version.
Migration runners serialize through the existing advisory transaction lock;
downgrade table locks also serialize the guard with application writes. The
migrator explicitly uses Read Committed so checks see commits made while waiting
for a lock, even when the connection defaults to Repeatable Read. No Kafka
I/O is added and no Outbox/Inbox lease or offset transition changes. Refused
migrations are observable errors and require operator investigation, not guessed
history repair. Locks are released on transaction end or lost connection.
At-least-once duplicates around a broker ACK remain possible as before.

## Later qualification

The wider local roadmap still includes production-size migration timing,
mixed-version process tests, multi-version infrastructure testing, restore drills,
retention diagnostics and longer managed-consumer soak. These are not replaced
by small integration fixtures and are not claimed complete here.
