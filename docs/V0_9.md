# v0.9 — operational readiness

Released baseline: [v0.8.0](https://github.com/EmitLane/emitlane/releases/tag/v0.8.0).
This candidate adds operational configuration and stronger recovery evidence on
schema version 4. No new schema migration or delivery state transition is added.

## Scope

- Relay database snapshot freshness and failure metrics distinguish current
  scrapes from stale queue/ordering observations.
- Starter Prometheus rules and a selectable Grafana dashboard cover queue age,
  dead/ordered blocks, managed consumer lag and pauses, saturation, control,
  presence, integrity and process trends. Rules and dashboard queries are checked
  in CI; thresholds and alert routing remain deployment choices.
- A real logical backup/restore fixture checks retained PostgreSQL protocol state,
  an atomic business/Outbox pair, ordered cursors and repeated migration safety.
- The opt-in managed consumer soak compares exact IDs and effects between
  independent producer business rows, Outbox, Inbox and a Kafka audit through
  captured end offsets. Equal counts cannot conceal substituted identities or
  corrupted effects. Broker duplicates are measured and allowed.
- Monitoring, deployment/probe, retention and restore reconciliation runbooks
  describe the limits of the evidence and operator decisions.

See [Monitoring](MONITORING.md), [Backup/restore](BACKUP_RESTORE.md) and
[consumer reliability](CONSUMER_RELIABILITY.md).

## Qualification boundary

Tests use PostgreSQL 16 and a single Kafka 4.3.1 broker. Multi-broker leader/ISR
faults, infrastructure version matrices, production-size PITR and restore timing,
24/72-hour memory trends and independent production pilots remain v1.0 gates.
Do not equate this candidate or a short managed soak with those qualifications.
The soak's seed labels the input payload; fault phases are fixed, not randomized.

## Crash and concurrency review

The runtime change only observes existing database snapshots. Process death
before/after metric updates may leave an incomplete scrape or reset counters on
restart; no database row, Kafka acknowledgement or offset is modified. No new
lease or state transition can lose an event, create a stuck lease or bypass fencing.
Concurrent relay delivery semantics remain at least once. Failed snapshots retain
old values and are visible through the new timestamp/counter. Recovery of those
observations is automatic after a successful snapshot; diagnosing a stale database
or reconciling restored Kafka offsets remains an operator task.
